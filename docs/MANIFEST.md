# Package and build manifests

WASM Zoo has two metadata layers.

## Catalog metadata

`packages/<slug>/package.json` is human-reviewed metadata: upstream pin, Zoo status, distributed profiles, release assets and curated target limitations.

`status=available` means a concrete build recipe exists and its meaningful runtime smoke test is expected to pass before release. Planned packages may track upstream without pretending a binary exists.

## Generated artifact metadata

Each builder emits `manifest.json` beside the Wasm files. A published build should record:

- exact upstream ref + commit;
- exact toolchain version + commit;
- upstream frontend/API shape used by the artifact;
- threading, SIMD, SharedArrayBuffer and filesystem requirements;
- external libraries actually linked;
- exact byte sizes and SHA-256 hashes.

Package-specific companion inventories are allowed. FFmpeg emits `features.json` plus `ffmpeg-config.mak`; libarchive emits `features.json` plus `libarchive-config.txt`.

A release also carries build information, applicable license notices, corresponding source/build recipe and `SHA256SUMS.txt`.

The catalog must never claim “full” means every feature of every native build. Target and optional-library gaps are part of the artifact identity.

## Published release metadata

An available package can declare a `release` object with the immutable tag, release page, asset base URL, corresponding-source asset and checksum asset. Each profile declares its exact `releaseAsset` filename and optional `playgroundPath`.

The catalog uses those human-reviewed names for stable links. It does not duplicate generated byte counts in package metadata. Pages stages the matching published artifact and reads `manifest.json` for actual Wasm/gzip sizes.
