# Supply-chain metadata

WASM Zoo v0.8.0 makes supply-chain evidence part of the build contract rather than a release-note convention.

## When metadata is created

`provenance.json` and `sbom.cdx.json` are generated by the host-side build wrapper **after** the package's real Chromium smoke test passes. A failed compile or failed browser smoke test therefore cannot produce a normal metadata-enabled release through the supported workflow.

The generator reads the built `manifest.json`, the reviewed `packages/<slug>/package.json`, immutable pins in `builders/<slug>/versions.env`, and any package-specific dependency inventory such as libvips `versions.json` or Ghostscript's bundled license inventory.

## provenance.json

The file is an in-toto Statement:

- `_type`: `https://in-toto.io/Statement/v1`
- `predicateType`: `https://slsa.dev/provenance/v1`
- `subject`: SHA-256 digests already recorded by the generated build manifest
- `buildDefinition.externalParameters`: package, profile, upstream version/ref and target properties
- `buildDefinition.resolvedDependencies`: pinned source repositories/commits, source-archive digests where available, and the Emscripten base image
- `runDetails`: local or GitHub Actions invocation identity plus browser-smoke-test byproduct status

The generator resolves the `emscripten/emsdk:<version>` OCI manifest digest with Docker Buildx when available. If that lookup is unavailable, provenance remains valid but marks environment completeness as incomplete instead of inventing a digest.

WASM Zoo uses the SLSA provenance data model; it does not claim a higher SLSA build level merely because this JSON exists.

## sbom.cdx.json

The SBOM uses CycloneDX 1.6 JSON. It describes:

- the Zoo package/profile as the metadata component;
- the exact upstream project;
- explicitly linked external libraries declared by the profile;
- package-specific generated inventories when available;
- Emscripten as a build tool rather than pretending it is shipped application code.

Some upstream source archives bundle third-party code without a single machine-readable version map. In those cases, such as Ghostscript, Zoo records the component families observable from the official source/license inventory and explicitly marks versions it cannot safely infer. The SBOM should prefer an honest partial field over a fabricated exact version.

## Release layout

A metadata-enabled profile ZIP contains:

```text
manifest.json
features.json
provenance.json
sbom.cdx.json
... runtime/package files ...
```

The GitHub Release also exposes:

```text
provenance-<profile>.json
sbom-<profile>.cdx.json
```

Both standalone files are included in `SHA256SUMS.txt`.

## Legacy releases

Package release tags are versioned independently from the overall Zoo catalog. v0.8.0 does not rewrite existing immutable package releases just to backfill metadata. Release Health reports older releases as waiting for the v0.8 metadata contract while continuing to check their build gate, release assets, Playground and upstream freshness.

## Validation

Run:

```text
npm run metadata:check
```

The check creates a synthetic manifest for every published profile and verifies that the metadata generator emits the expected in-toto/SLSA and CycloneDX headers, subject digest and profile identity. It also checks every builder and release script for the metadata handoff contract.
